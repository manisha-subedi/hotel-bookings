Two hotels, 119,390 bookings

This is real booking data from two hotels in Portugal. One is a resort in the Algarve. The other is a city hotel in Lisbon. The data covers three years, from July 2015 to August 2017.

First I built a Power BI report from it. Then I made this page from the same data, with three parts: the numbers a hotel manager checks every month, a small tool that tells you how often a booking like yours gets cancelled, and a tool that tells the hotel how many extra rooms it can sell.

The Power BI report

The report has an overview, demand and channels, customers, cancellations, and a page with the single bookings behind any chart. The data model is a star schema with six tables and 43 DAX measures. The numbers are the same as on this page.

3. How many extra rooms can the hotel sell?

Hotels sell more rooms than they have. This sounds strange, but it makes sense. Some bookings always cancel. If the hotel sells exactly its number of rooms, some rooms stay empty every night. So hotels sell a bit more. The question is, how much more?

If they sell too few, rooms stay empty. If they sell too many, a guest arrives and there is no room. The hotel has to send them to another hotel and pay for it. Both are bad. This tool finds the best middle.

One important thing. The right cancellation rate is not the 37 percent from above. Most of those bookings cancel weeks before arrival, and the hotel sells the room again. What matters is the bookings that are still there a few days before arrival. How many of those still cancel or do not show up? For the city hotel it is 8.5 percent one week before. For the resort it is 4.8 percent. You can pick a different number of days, or type your own rate.

Then set two costs. What does an empty room cost the hotel? What does it cost to send a guest away? The chart shows the expected cost for each number of extra bookings. The lowest point is the best number.

How I built this

The data comes as one big flat table with 32 columns. First, I split it into a star schema in DuckDB. That means one main table of bookings, one table of room nights, and four small tables for dates, hotels, customers, and booking channels. The date table is used two times. Once for the arrival date, and once for the day the booking was cancelled.

The data does not say how many rooms each hotel has. So I estimated it. I looked for the night with the most rooms occupied. That gives 226 rooms for the city hotel and 187 for the resort. Then occupancy is rooms sold divided by rooms available.

A common mistake is to divide by booked nights instead. That gives 100 percent every month, which is wrong. I wrote a test that fails if this ever happens.

All the numbers on this page are computed once, when the site is built, and saved as small JSON files. The page reads them and draws the charts. There is no server and no machine learning model. The code, the SQL, and the tests are on GitHub.
